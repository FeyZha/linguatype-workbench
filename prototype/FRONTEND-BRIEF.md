## 1. 用户与核心任务

### 目标用户

正在练习 IELTS Writing Task 2 的中文母语学习者。他知道自己想表达什么，也愿意自己写，但会在某个英文句子里因为不会表达一段中文意思而卡住。

### 用户真正要完成的事

不是“让 AI 写作文”，而是：

1. 先用中文占住不会表达的位置，不中断写作。
2. 只处理当前最卡的一句。
3. 获得足够继续写下去的表达块，而不是完整答案。
4. 自己决定取舍、顺序、词形和接入方式。

### 体验原则

- 写作区永远是主角，帮助区是按需出现的副手。
- 用户原文永远可控；任何生成、失败、揭示或反馈都不能自动改文。
- 首屏给得克制，用户主动点开后才逐步增加帮助。
- 界面要让用户清楚知道：当前处理的是哪篇作文、哪一句、哪一块中文。

## 2. 唯一页面与完整流程

产品只有一个写作工作台。新建作文、题库选择、归档管理可用弹窗、抽屉或浮层完成，但不要拆成独立页面，也不要引入第二条产品链路。

主流程：

1. **选择起点**：从原创题库选题，或自行输入题目，创建一篇作文。
2. **持续写作**：用户在全文编辑区写英文；不会表达时保留中文占位。
3. **本地发现卡点**：页面列出全文中所有含中文的句子，不调用模型。
4. **选择一句**：用户点击某一句的“处理本句”；没有题目时不能发起。
5. **一次生成**：前端提交题目、当时的完整全文和目标句；同一句进入独立的处理中状态。
6. **展示结果**：
   - 简单项直接展示一个英文表达。
   - 复杂项首次只展示 2–3 个中文语义支架，所有对应英文均隐藏。
7. **按需揭示**：用户可依次揭示任意一个或多个英文；已揭示内容保持可见，揭示过程不发请求。
8. **用户自己续写**：用户回到原文，自行移动、变形、组合或舍弃支架；系统不自动应用。
9. **留下反馈**：可标记“有帮助 / 没帮助”，没帮助时可选原因；这不触发模型调用。
10. **继续处理**：用户可在同一篇作文处理其他句子，也可切换到另一篇作文；各自状态互不串用。

## 3. 页面结构与组件清单

视觉形式可以变化，但下列职责都需要有清晰归属。

### A. 全局框架

- 品牌与“内部原型”标识。
- 当前本地保存状态：正在恢复、已保存、保存失败。
- 单页工作台容器。

### B. 作文库

- 新建作文入口。
- 进行中的作文列表、当前作文标识、更新时间。
- 归档当前作文、查看归档、恢复、永久删除。
- 永久删除必须二次确认，并明确“无法撤销”。
- 若最后一篇进行中的作文被归档或删除，自动保留一个可继续使用的空白作文。

### C. 新建作文弹窗

- 两种模式：原创练习题 / 自己输入题目。
- 原创题按“全部、教育、科技、社会、环境、工作”筛选。
- 题目卡展示标题、主题、题型、难度和已使用次数；提供完整题目预览。
- 自定义题目为空时不能创建。
- 支持关闭、Esc 退出，并在关闭后把焦点还给打开弹窗的按钮。

### D. 写作区

- 雅思题目编辑框。
- 题目来源提示；若来自题库，保留“原创题目、主题、标题”的来源感知。
- 作文全文编辑框。
- 单词数和本地保存状态。
- 明确提示“中文占位不会被自动替换”。

### E. 卡点识别区

- 空态：没有中文占位。
- 有结果：逐句列出所有含中文的句子及顺序。
- 每句只对应一个处理记录；重复点击已处理句子只打开原记录，不新建请求。
- 句子按钮状态：处理本句、正在准备、查看支架、查看失败。

### F. 表达支架区

- 本篇已处理句子的历史切换器，并显示处理中、已生成、失败。
- 未选择记录时的引导空态。
- 处理中、失败、成功三种主状态。
- 成功结果按原中文片段分组，顺序与接口返回一致。
- 简单表达卡。
- 复杂支架包：中文支架、隐藏/已揭示英文状态。
- 反馈区及可选失败原因。
- 内部测试记录下载入口。
- 固定提醒：“系统不会自动应用、替换或完成整句”。

## 4. 状态归属与隔离规则

这是前端重设计最容易出错的部分。

### 每篇作文独立保存

每篇作文拥有自己的题目、全文、题目来源、已处理句子、已移除句子记录、当前查看的句子和归档状态。切换作文时，界面必须完整恢复该作文自己的内容，不得显示上一作文的支架、揭示状态、反馈、错误或加载状态。

### 每个句子独立保存

每个已处理句子拥有自己的请求快照、加载/成功/失败状态、生成结果、已揭示支架、反馈和错误信息。切换句子时不得共用这些状态。

实现上继续使用 `documentId + cardId` 作为记录身份，`cardId` 创建后不可变化；请求无论何时返回，都只能按原 `documentId + cardId` 回填。句子定位和编辑后的追踪必须复用 `app/sentence-tracking.ts` 与现有 `SentenceSpan`，不得另写一套按文本猜测或按邻近卡片挂载的规则。

### 请求快照与实时正文分开

发起处理时冻结一份“当时的题目、全文、目标句、时间”。用户之后继续编辑正文，不得悄悄改写这次请求对应的结果或把结果挂到别的句子上。

### 编辑后的句子追踪

- 句子仍可定位：保留原处理记录，并跟随句子的新位置。
- 整句被删除或已无法可靠定位：从当前记录中移走，保留到该作文的内部历史记录中。
- 失败后目标句已不含中文：不可重试。
- 任意情况下都不能自动把表达写回正文。

| 作文 | 已归档 | 只在归档区出现 | 恢复、永久删除 | 0 |

| 新建弹窗 | 题库模式 | 分类、题目列表、预览、已使用次数 | 筛选、选择、创建、关闭 | 0 |

### 5.2 写作与卡点识别

| 状态 | 用户看到什么 | 主动作 | 约束 |
|---|---|---|---|
| 题目为空 | 题目输入提示 | 填写或选择题目 | “处理本句”不可用 |
| 正文为空 | 鼓励先写、允许中文占位 | 输入正文 | 不调用模型 |
| 正文无中文 | “当前没有中文占位” | 继续写作 | 不显示虚假卡点 |
| 正文有 1 个含中文句 | 该句原文和“处理本句” | 发起处理 | 一次只处理这一句 |
| 正文有多个含中文句 | 按全文顺序列出 | 任选一句处理 | 不批量处理 |
| 句子已有记录 | “查看支架/查看失败/正在准备” | 打开原记录 | 不重复创建记录 |
| 已处理句子位置变化 | 记录仍指向同一句 | 查看原记录 | 不串到其他句子 |
| 已处理句子被删除 | 当前列表不再显示该记录 | 继续写作 | 记录仅留在该作文内部历史/导出中 |

### 5.3 请求与支架区

| 状态 | 必须展示 | 用户可做什么 | 网络行为 |
|---|---|---|---|
| 尚无处理记录 | 选择含中文句子的引导 | 回到卡点列表选择 | 0 |
| 有记录但未选中 | 选择一条记录的引导 | 切换历史记录 | 0 |
| 处理中 | 当前目标句、克制的等待提示、“只调用一次” | 切换到别的作文或句子继续写 | 仅初次 POST 1 次 |
| 失败 | 安全错误文案、“没有修改你的原文”、重试按钮 | 重试或继续写 | 点击重试才新增 1 次 POST |
| 成功：简单项 | 原中文 + 唯一英文表达 | 阅读、自行接入原句 | 0 |
| 成功：复杂项初始 | 原中文 + 2–3 个中文语义支架；英文全部不可见 | 选择任意中文支架揭示 | 0 |
| 成功：复杂项部分揭示 | 已选项显示英文；未选项仍只显示中文 | 继续揭示任意项 | 0 |
| 成功：复杂项全部揭示 | 所有英文保持可见，但不拼成完整句 | 自行取舍、回原文编辑 | 0 |
| 成功：多中文片段 | 每个顶层中文片段独立成组、顺序不变 | 分别阅读/揭示 | 0 |
| 反馈未选 | “有帮助 / 没帮助” | 选择反馈 | 0 |
| 反馈有帮助 | 选中态清晰 | 可改选 | 0 |
| 反馈没帮助 | 选中态 + 可选原因 | 选原因或改选 | 0 |
| 页面重载后恢复 | 每篇、每句原有结果及揭示状态 | 继续原流程 | 恢复本身 0 |

> “复杂项首屏隐藏”是硬性规则：接口虽然一次返回全部英文，但初次成功界面不得通过正文、预览、无障碍名称、提示文本、折叠内容或动画瞬间泄漏未揭示英文。

## 6. 数据与接口边界

前端只负责收集上下文、展示结果和保存本地交互状态；后端负责锁定中文片段、决定帮助类型并生成内容。

### 唯一接口

- 方法与路径：`POST /api/scaffold`
- `contracts/scaffold-api.v1.openapi.json` 是唯一运行时规范；前端从 `app/scaffold-api-contract.ts` 引用路径和类型，不在页面里重复写一套协议。
- 版本：`1.0.0`；所有响应带 `x-linguatype-api-version`。

请求边界：

- `taskPrompt` 去除首尾空白后为 1–4000 字符。
- `fullEssay` 去除首尾空白后为 1–20000 字符。
- `targetSentence` 去除首尾空白后为 1–3000 字符，必须包含 `\u3400-\u9fff` 范围内的中文字符，并逐字存在于本次 `fullEssay`。
- 页面只用现有 `app/sentence-tracking.ts` 找到可点击的完整句子；不得在浏览器继续切分 `sourceZh` 或判断帮助类型。

请求只包含：

| 字段 | 含义 |
|---|---|
| `taskPrompt` | 当前雅思题目 |
| `fullEssay` | 发起时的完整作文 |
| `targetSentence` | 用户选择的、仍包含中文的目标句 |

成功结果必须原样尊重：

- `sourceZh` 与 `action` 由产品侧决定，前端不得重新切片、改序或改路由。
- `provide_expression`：立即显示唯一 `recommendedExpression`，`scaffolds` 为空。
- `offer_scaffolds`：`recommendedExpression` 为空；必须一次收到 2–3 个 `scaffolds`。前端只按 `action` 渲染，不自行判断“简单/复杂”。
- `meta.callCount` 固定为 `1`；可展示耗时和模型信息，但不得让它抢占主要体验。

失败结果：

| HTTP | 错误码 | 前端含义 |
|---|---|---|
| 400 | `INVALID_INPUT` | 题目/全文/目标句缺失或不匹配，或目标句没有中文 |
| 502 | `SCAFFOLD_GENERATION_FAILED` | 上游请求或生成结果不可用 |
| 503 | `MODEL_NOT_CONFIGURED` | 内部模型尚未配置 |

所有失败统一遵守：展示安全文案、保留用户原文、保留错误在当前作文的当前句子内，不影响其他句子。

网络中断、请求被取消、非 JSON 响应、`200` 但结构不符合 OpenAPI、版本响应头缺失或不为 `1.0.0`，也一律进入当前卡片的安全失败状态；不得展示半成品或改动原文。版本号只校验响应头，不作为额外请求头发送。重试必须由用户主动触发，并使用当前仍可定位的目标句、当前题目和当前全文生成新的请求快照；目标句已经不含中文时不可重试。

### 本地状态

- 作文库、正文、支架结果、揭示状态和反馈均保存在当前设备。
- 继续复用 `app/workspace-state.ts` 中的 `WORKSPACE_KEY`、`LEGACY_DRAFT_KEY`、v1→v2 迁移、`SupportCard` 和 `ArchivedCard`；视觉重构不得破坏已有本地数据恢复。
- 揭示使用句子内的独立本地状态；点击揭示时禁止 `fetch`、重新提交或刷新结果。
- 已揭示内容在切换句子、切换作文和页面重载后仍保持可见。
- 反馈值保持 `helpful | not_helpful | null`；“没帮助”的可选原因保持 `inaccurate / unnatural / too_much / too_little / other`，可以重做呈现但不新增枚举。
- 下载继续沿用现有 `recordVersion: 3` JSON 结构，包含当前作文快照、可见与已移除卡片及导出时间；可以重做入口，但不改变字段语义。
- 不记录或显示 API Key、完整请求头等凭证。

## 7. 不可改变的产品约束

1. 一次只处理一个含中文的目标句。
2. 每次处理使用题目、完整全文和目标句作为上下文。
3. 同一句首次处理只发起一次模型请求；复杂支架在这一次内全部预生成。
4. 每个具体语义支架只给一个英文表达，不提供英文候选列表。
5. 前端只按接口 `action` 展示；`provide_expression` 只有一个英文表达，`offer_scaffolds` 必须有 2–3 个中文语义支架。
6. 复杂项的英文初次全部隐藏，逐个揭示，揭示为零请求。
7. 用户可以揭示多个，已揭示内容持续可见。
8. 即使全部揭示，也不能预先拼成完整命题或完整句。
9. 不自动插入、替换、应用或改写原文。
10. 不做整句生成、全文批改、评分、续写、观点生成或批量处理。
11. 不把产品做成通用翻译器、聊天机器人或写作代办。
12. 不新增第二条高频流程，不引入学习资产、RAG 或复盘闭环。

## 8. 响应式要求

### 桌面

- 写作区占主要宽度，支架区与目标句保持同时可见。
- 作文库可以横向、侧栏或紧凑导航呈现，但不能挤压正文到难以写作。
- 长作文与长支架各自滚动时，当前作文和当前句的归属始终清楚。

### 平板

- 优先保留写作区；作文库可折叠，支架区可并排或从侧边展开。
- 打开支架不得清空编辑光标或丢失未保存内容。

### 手机

- 使用单列顺序：当前作文 → 题目/正文 → 卡点 → 支架。
- 可用固定切换器在“写作 / 支架”之间移动，但它们必须是同一页面、同一状态。
- 揭示后应把新出现的英文带入可视区域，同时避免页面突然大幅跳动。
- 所有点击目标至少约 44×44 px；不依赖悬停才能操作。

---

## 9. 可访问性要求

- 中文为主要界面语言；字段、按钮和状态使用直接、可理解的中文。
- 所有输入都有持久可见的标签，不能只靠 placeholder。
- 键盘可以完成新建、选题、写作、选句、揭示、反馈、归档和关闭弹窗。
- 弹窗打开时焦点进入弹窗并被约束在其中；关闭后回到触发位置。
- 处理中、保存成功和失败等变化通过适当的状态播报告知读屏用户，但避免每次输入都播报。
- 失败使用 `alert` 语义；状态不能只靠颜色区分，需同时有文字或图标。
- 揭示按钮要说明对应中文支架及当前“未揭示/已揭示”状态；未揭示英文不能进入可访问名称。
- 正文、支架英文和关键操作满足 WCAG AA 对比度；焦点样式清楚可见。
- 支持 200% 文本缩放、系统减少动态效果设置和窄屏横向不溢出。

---

## 10. 视觉与文案方向

- 气质：安静、可信、专注写作；像一张有结构的写作桌，而不是 AI 对话框。
- 信息层级：原文最高，中文卡点其次，帮助按需出现，模型信息最低。
- 不使用“AI 已为你完成”“一键优化”“立即替换”等接管式文案。
- 处理中不承诺质量；失败明确告知原文未改变。
- 可以重新设计色彩、字体、卡片、间距和动效，但不要用装饰掩盖当前作文、当前句和揭示状态。
